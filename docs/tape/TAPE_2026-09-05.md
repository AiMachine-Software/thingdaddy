## B · 1 · THE STALE BUILD — a port that answers is not a build that serves

```
bun src/server.ts   pid 24899   started Sat 22 August 19:28
                                RUNNING FOR TWO WEEKS
```

The screens showed five empty pillars all afternoon. The banner read **LIVE ·
102,472 records (101,626 candidate · 778 exception · 68 verified)** the entire
time, and `/health` answered `ok:true`. Three routes the screens call returned:

```
{"error":"no route GET /party/4153997/completeness"}
{"error":"no route GET /node/by-legacy/party/4153997"}
```

**`server.js` on disk defines both.** The running build predated them by a
fortnight. Killed it, started `node server.js` from the current repo, and all
six routes came back present.

**THE TELL WE ALMOST MISSED.** Both a stale build and an honest empty answer
return **404**. Only the body distinguishes them:

```
STALE     "no route GET /node/by-legacy/party/4153997"
CURRENT   "no spine node backfilled for party 4153997"
```

Same status code, opposite meanings. The screens cannot tell them apart and
neither could we, for most of an afternoon. **This is canon §7's first family
wearing a new coat: a check that cannot return its own failure — here, a
liveness probe that reports a connection while the build behind it is absent.**

**BUILD DRIFT is now a named watcher (Part D).** It watches our own machine,
and it is the least glamorous of the four.

## B · 2 · MEDFARE — the resolver caught what a registry cannot

A search for Diazyme's verified prefix `0817089` returned **three** party rows:

```
4047358   MedFare LLC       prefix 081708901   GLN 0817089010017   GDSN
4153997   DIAZYME LABS      prefix 0817089     hand-read            GUDID
4047388   Medfare, LLC      no prefix          exception            GDSN
```

**`081708901` contains `0817089`. GS1 licences do not nest.** If `0817089` is a
valid 7-digit GCP — and it is, KJ hand-read it against Verified by GS1 — then
those digits are inside Diazyme's number space and Diazyme allocates them.

**KJ's correction, and it is the sharper reading:** *"a GLN is a subset of a
prefix .. medfare can not generate a gln ? they can not generate a gtin"*

The defect is not the digits. **It is the attribution.** MedFare did not
generate `0817089010017`; the licensee did. The row says MedFare *holds* a
prefix. It does not. It appears in GDSN carrying a location number issued
inside someone else's licence.

**Distributor-as-directory (`HARVEST_UNIFIED_SPEC` §4.2) one level down.**
Yesterday it was Walmart holding other manufacturers' prefixes. Today it is a
GLN inside another company's licence read as its own root.

**FOUR CAUSES LOOK IDENTICAL AND WE MUST NEVER DISTINGUISH THEM:**

```
a bad cut by our own loader
a mis-filing by them
a subsidiary or sales channel filing legitimately inside the parent licence
genuine misuse
```

**KJ:** *"medfare could be a diazyme subsidiary .. its an llc maybe they use
medfare to sell through?"* Entirely possible — and it does not change the
register's answer, only whose answer it is. Under prefix-as-key it renders
correctly either way:

```
WRONG   MedFare LLC · prefix 081708901 · a party in its own right
RIGHT   0817089 (Diazyme)
          └─ GLN 0817089010017 · claimed by "MedFare LLC" · GDSN · dated
```

`issued-inside`, not `equals`. The containment is a **fact**; the reason is the
licensee's to state.

**NOBODY ASKED FOR THIS FINDING.** It arrived in the ordinary course of
resolving a prefix. **KJ:** *"this is what a resolver catches … its proving a
success not a failure."* A resolver that never surfaced anything unexpected
would be a directory.

## B · 3 · THE DROPPED ROW — a completeness failure under a completeness banner

```
search "diazyme"    2 rows   4153997 (0817089) · 4083490 (no prefix)
search "0817089"    3 rows   4047358 · 4153997 · 4047388
```

**Party 4083490 — the unrooted Diazyme — vanishes from the prefix search.** Same
company. The prefix query matches on the prefix column only, so a row with
`prefix NULL` cannot match and no other field is consulted.

**The two searches return disjoint, incomplete answers to the same question.**
And the banner reads *"3 party rows — duplicates are shown, never merged
silently."* The register held four relevant rows and showed three.

**That is the sharper defect of the two.** The extra MedFare rows are a
containment finding in the wrong place — informative. **A dropped row is a
completeness failure under a banner asserting completeness.**

Fix: resolve the prefix, show containment findings *separately*, and return
every row bearing on the company including those with no prefix. KJ: *"if a
company only enters company name they get one view which should be the correct
view."*

is unsolved, and it reframes the pre-built page: **not a marketing artefact —
the mailbox.** *Here is your page, and the network has something to tell you.*
One of those gets opened.
