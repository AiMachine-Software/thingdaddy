**THE RULE.** A GS1 company prefix is the key, because an authority issued it.
**There is no primary prefix — only peers.** Everything else — which name,
which URL, which party row, which is stale — belongs to the customer.

```

NO PRIMARY          Which one matters is the licensee's decision, never ours.
NO MERGE            Two party rows with one name is a FACT ABOUT THE REGISTER,
                    not an error in it. Publish both, source and date on each.
NO SUPERSESSION     We do not retire a row nobody asked us to retire.
THE ADDRESS IS THE  thingsite/0817089 — not a company slug. This also kills the
PREFIX              constructed-hostname defect: there is nothing to construct.
NO PREFIX,          General Atomics gets the get-a-prefix on-ramp, not an
NO THINGSITE        empty site. Structural now, not a policy.
```

This extends §6.1 (3 Sept — *the prefix is the association; a company name is
an attribute on the prefix row; party is not the join*) and it is enforced by
Law 7: **a ThingSite is a mirror. Publish what is found as found; the owner
corrects it; ThingDaddy does not edit.**

## A · 1 · Why the mirror is the agent-centric choice — not merely the honest one

**KJ:** *"the easiest way to create conflict for a machine or network is
manufacture the error yourself."*

A merge is a manufactured error: a fact no authority issued, written once and
carried forever. And the machine cannot detect it afterwards, because the
evidence was destroyed at write time.

```
MERGED     "Diazyme, prefix 0817089"
           one row · nothing to check · nothing to disagree with
           WRONG SILENTLY, PERMANENTLY

MIRRORED   prefix 0817089 · named Diazyme Laboratories Inc by GUDID,
           hand-read 30 Aug, party 4153997
           prefix … · same name, different source, different date
           the agent WEIGHS, and can be wrong OUT LOUD
```

**Merge on write and you decide for every future reader, once.** Merge at read
time and each agent decides for its own purpose — a regulator's question and a
procurement question want different answers from the same rows.

This is the same rule as *null is a refused key, never a guess*. A guessed value
and a merged row are both us inventing the thing the network was meant to
resolve.

**And it is the one property nobody can copy by scraping.** Anyone can assemble
a confident record. Nobody else can hand an agent the disagreement.

## B · 1 · NEW RULE — read a gate before you work it

> **When a gate refuses at volume and no other gate fires, the refusal is a
> ruling the data is making. Stop working the queue and read it.**

A refusal looks like work: it has a count, it sits in a queue, the number goes
down if you push. **The queue was an answer wearing the shape of a backlog.**

Composes with the standing rule *the gate refusing IS the product* — which we
wrote, and then did not apply to ourselves.

## C · 2 · The failing test suite is a gate working

17 test files, no `test` script in `package.json` — **the suite cannot be
invoked as a suite.** Under Node 24 it also needs a glob, not a directory.

They fail against a running server. At least one fails because
`party_needs_stage_ancestor` refuses a fixture inserted straight into production
at `verified`. **The test predates the constraint.**

> **The correct fix is fixtures that go through staging like everything else.
> NOT relaxing the constraint so the suite goes green.** Stated because the
> tempting fix is the wrong one, and a suite made green by loosening a gate is
> worse than a red one.
